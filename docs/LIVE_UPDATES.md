# Обновления Homie внутри Android-приложения

## Что готово

Android проверяет подписанный `https://homie-web.app/updates/<runtime>/latest.json`
при холодном запуске. Если есть новая версия, показывает загрузку с реальным
процентом, проверяет SHA-256 архива и перезапускает WebView. Нет обновления —
открывается обычный интерфейс. При ошибке доступны повтор и текущая версия.
Браузерная версия продолжает обновляться обычным деплоем сайта.

Используется открытый плагин `@capgo/capacitor-updater` для Capacitor 7 в ручном
режиме. Облачный сервис Capgo и его статистика отключены. Пакеты хранятся у нас.
Описание пакета подписывается RSA-PSS/SHA-256; публичный ключ закреплён в приложении.
Плагин проверяет SHA-256 ZIP. Не меняйте протокол/публичный ключ в существующем
runtime без плана миграции доверия.

Обновляется HTML/CSS/JS и изображения. Нативные плагины, разрешения, SDK и Java
требуют новой APK. Скрипт откажется публиковать OTA, если изменился fingerprint
Android-кода/конфигурации или версии нативных зависимостей.

## Один раз: APK и настройка сервера

1. Установить новую APK с механизмом обновлений (текущий релиз: versionCode 3,
   versionName 2.0.1, runtime 2.0.1).
   Старые установленные APK этот механизм получить через сайт не могут.
   Для пользователей обновление APK должно быть подписано тем же Android-ключом,
   что и установленная версия. Debug APK предназначена для тестирования.
2. Ключ OTA создан локально: `.ota/private.pem`. Он исключён из git.
   Публичная часть находится в `src/app/core/ota-trust.json` и коммитится.
   Сделайте защищённую резервную копию приватного ключа. Не запускайте `ota:init`
   заново и не генерируйте другой ключ на сервере: установленная APK доверяет
   уже закреплённому публичному ключу.
3. Передайте приватный ключ по SSH на сервер в `/opt/eat-it/ota-private.pem`,
   назначьте владельцем пользователя деплоя и права `600`. Не помещайте его в web root.
4. На сервере нужен `zip`: `sudo apt install zip`.
5. Создайте каталог пакетов (пример для пользователя `deploy`):

   ```sh
   sudo install -d -o deploy -g www-data -m 755 /var/www/eat-it/updates
   ```

6. Добавьте **только блок `location ^~ /updates/`** из
   `deploy/nginx-homie-web.app.conf` в действующий HTTPS server-блок homie-web.app.
   Не заменяйте рабочую TLS-конфигурацию целиком. Проверьте и перечитайте Nginx:

   ```sh
   sudo nginx -t
   sudo systemctl reload nginx
   ```

   Публичные файлы OTA не требуют авторизации. CORS разрешает загрузку из локального
   Android WebView. Каталог отдельный от статики сайта, поэтому веб-деплой с
   `rsync --delete` его не удаляет. Список файлов не публикуется.

## Выпустить обновление прямо с сервера

В рабочей копии проекта после правок:

```sh
npm ci
npm run db:generate
npm test -- --watch=false
npm run test:server
npm run test:ota
npm run ota:publish -- --key /opt/eat-it/ota-private.pem --output /var/www/eat-it/updates
```

Команда сама создаёт production-сборку и ZIP без source maps, подписывает описание
и атомарно заменяет `latest.json` после размещения ZIP. Закрытый ключ в архив не
попадает. Параллельные публикации в один runtime блокируются `.publish-lock`.
После аварийного завершения удаляйте этот каталог только убедившись, что процесс
публикации уже не работает.

Backend-изменения сначала задеплойте и проверьте healthcheck. Старые мобильные
версии продолжают работать с API: сохраняйте обратную совместимость.
Изменения в рабочей копии на сервере фиксируйте коммитом и push в git: существующий
GitHub workflow обновляет сервер через `git reset --hard origin/main` и уничтожит
незакоммиченные изменения. Предпочтительна отдельная рабочая копия для разработки.

После push в main существующий CI собирает APK-артефакт и деплоит сервер.
После успешного healthcheck он публикует OTA, **если ключ уже настроен** по пути
выше. Если ключа нет, workflow явно пишет, что OTA пропущено. Публикация пакета
не отправляет APK в магазин и не заменяет Android-подпись.

## Откат и неисправная версия

После первого рендера Angular вызывается `notifyAppReady`. Если JavaScript новой
версии не запускается, плагин возвращает предыдущую рабочую версию по таймеру
30 секунд. Пометка неудачной версии сохраняется, чтобы не зациклить установку.
Это защита от сбоя запуска, а не автоматическая диагностика всех бизнес-функций.

Для ручного исправления откатите ошибочный коммит в рабочем коде и снова выполните
`ota:publish`: старый рабочий код получит новый номер выпуска. Простая подмена
`latest.json` старым описанием не сработает на устройствах, уже увидевших больший
номер: это защита от повторной установки старых пакетов.

## Когда изменилась нативная часть

1. Увеличьте `versionCode` и `versionName` в `android/app/build.gradle`.
2. Синхронизируйте Android: `npm run android:sync`.
3. Запишите новый runtime, совпадающий с новым versionName, например:

   ```sh
   npm run ota:runtime -- --runtime 3.0.0
   npm run android:apk
   ```

4. Выпустите новую APK. OTA для неё попадут в отдельный каталог `/updates/3.0.0/`.
   Для старого runtime оставьте последний совместимый пакет.

## Проверка перед распространением

На тестовом Android: установить APK → запустить без сети → открыть текущую версию;
затем включить сеть, опубликовать пакет с заметным изменением → полностью закрыть и
снова открыть приложение → проверить проценты и новую версию. Повторный запуск
не должен снова скачивать тот же пакет. На тестовом runtime отдельно проверить
обрыв загрузки, неверную подпись/хеш и ZIP с неработающим JavaScript: последняя
проверка должна закончиться возвратом к прежней версии.

Магазины по-прежнему требуют соблюдать правила для загружаемого JavaScript;
OTA не заменяет проверку допустимости изменений и новую APK для нативного кода.
